## 1. Input Overview

The main input types are:

- layout mask `.npz` files
- layout registry/config files
- CLI parameters
- paper plotting CSV inputs

## 2. Layout Mask Inputs

Layout masks are `.npz` files that represent warehouse geometry as metadata plus binary grid layers. They are stored under `data/`, primarily in `data/instances/masks/`.

The core loader normalizes masks before optimization or preview. At a practical level, masks can include warehouse geometry layers such as walls, doors, reserved cells, restricted cells, pillars, storage cells, pick faces, and aisle-related layers.

The loader code recognizes these mask layer keys:

- `walls`
- `doors`
- `reserved`
- `restricted`
- `pillars`
- `storage`
- `pick_faces`
- `aisle`
- `aisle_h`
- `aisle_v`
- `aisle_cross`

It also recognizes generic aisle aliases such as `aisles`, `forced_aisle_horizontal`, and `forced_aisles_vertical` during normalization. Scalar metadata includes layout dimensions and aisle width when present. Exact keys can still depend on the mask file and loader normalization.

## 3. Layout Registry/Config Inputs

Layout registry/config inputs identify which mask files are available to the editor and runners. `configs/layouts.json` or equivalent registry/config data is used to track layouts.

The clean public release distinguishes optimization layouts from reference/comparison-only layouts:

- `AT_1.npz` through `AT_13.npz` are reference/comparison-only layouts.
- `AT_1.npz` through `AT_13.npz` should not be used for optimization runs.
- `AT_S_comercial_layout_AW_3.npz` is an optimization layout.

See `docs/layout_data.md` for full layout details.

## 5. Optimization Outputs

Optimization outputs are written under `results/` unless another output folder is provided. `results/` is ignored by Git.

Typical outputs include:

- CSV summaries
- JSON metadata
- optional saved layout archives
- rendered layout images if rendering is run

Experiment-level outputs can include `experiment_metadata.json` and `experiment_summary.csv`. Run-level outputs can include run metadata, candidate rows, generation summaries, profiling files, generation-objective evidence, and optional archive files.

The paper campaign wrapper additionally writes per-task logs and campaign manifests under its `--campaign-root`.

## 6. Archive Outputs

Layout archives are saved only when archive options are enabled through the experiment manager. Archive saving is controlled by options such as:

- `--archive-layouts`
- `--archive-rank-max`

Archive files can include saved `.npz` layouts and matching JSON index files. Archive rank filtering is controlled when saving archives through manager options and when rendering archives through renderer filter options.

Paper campaign tasks request both generation-elites and final-ranked archives.

Rendered archive layouts can be generated later using the rendering utilities. See the rendering section of `docs/cli_commands.md`.

## 7. Rendering Outputs

Layout rendering utilities generate images from saved layouts or archive folders. Rendering outputs are PNG files written to the requested output folder or to a default folder near the archive.

Coordinate labels, legend visibility, layout-count limits, title formatting, and resolution depend on rendering CLI options. Paper-style plots are separate from archive layout rendering.

## 9. Paper Pareto Plotting Inputs and Outputs

The paper-style Pareto plotting script uses inputs from:

`data/plot_inputs/paper/`

Required paper plotting CSV inputs include:

- `121_atefeh_published_reference_metrics.csv`
- `121_atefeh_rank03_points.csv`
- `121_kov1ow4_rank03_points.csv`

Outputs are generated by:

`whl_visualization/paper_pareto_plots.py`

The script writes paper-style figure outputs and an audit report under `whl_visualization/`. Paper-style Pareto plotting is separate from editor preview and from archive layout rendering.

## 10. Reproducibility Notes

Use fixed seeds for reproducible optimization runs. Bounded validation commands use explicit small parameters; paper-scale structural experiments use the campaign wrapper with `auto_from_instance` budgets and figures disabled.

The default paper campaign sets are:

- Phase 11: Proposed, random-restart BS, and BS-only;
- Phase 12B: V1-V5 only;
- Phase 12C: V6 and V7.

Phase 12B V0 is not generated as a duplicate campaign. The Phase 11 `proposed_nsga2_bs` results for matching instances and seeds are the V0/full-proposed baseline used during Phase 12B analysis. V6b is run separately when the binding-depth diagnostic is required.

## 11. Files Not Committed

These files and folders are not meant to be committed:

- `results/`
- `.venv/`
- `__pycache__/`
- temporary logs
- generated validation outputs

Curated reviewer-facing CSV/JSON evidence stored under documented `data/` paths is intentionally versioned.
